# Клубы, команды и рейтинг соревнований — дизайн-спека

Статус: **брейнсторм завершён, готово к формальному планированию/реализации**. Реализация ведётся в два этапа: сначала клубы и команды (без них рейтинг не имеет владельца), затем рейтинг соревнований поверх готовых клубов.

Кросс-проектность: домен затрагивает `competra-android`, backend `eSport` и, позже, `competra-web`. Первый этап реализации — Android + eSport backend. Web добавляется отдельной задачей.

---

## Часть 1. Клубы и команды

### Мотивация

Рейтинг соревнований должен принадлежать какому-то постоянному сообществу, а не отдельному пользователю или разовому соревнованию. Такой сущности («клуб») в проекте сейчас нет — у участника соревнования есть только свободное текстовое поле `commandName`, ни на что не ссылающееся.

### Сущности

**Club**
- `id`
- `name: String`
- `description: String`
- `foundedAt` — заполняется автоматически датой создания клуба, руками не задаётся
- `allowJoinRequests: Boolean` — разрешён ли приём заявок на вступление извне (клуб при этом всегда публичный и виден в поиске/списке всем; флаг влияет только на возможность подать заявку)

**ClubMember** (членство пользователя в клубе)
- `clubId`
- `userId` — членом клуба может стать только зарегистрированный пользователь с `userId` (гостевые/анонимные участники не допускаются, в отличие от `Organizer`/`Participant`)
- `role: ClubRole` — `FOUNDER | ADMIN | MEMBER`
- `joinedAt`

Один пользователь может состоять в нескольких разных клубах одновременно.

**Роли на уровне клуба (`ClubRole`)**
- `FOUNDER` — полные права; управляет составом, командами, заявками, может назначать/снимать `ADMIN`; может передать свою роль другому участнику клуба
- `ADMIN` — назначается Founder'ом; управляет составом, командами, заявками на вступление; не может распустить клуб и не может сместить Founder
- `MEMBER` — обычный участник без прав управления

Правила по Founder:
- Founder может передать свою роль другому участнику клуба
- Если Founder в клубе один — он **не может** просто покинуть клуб; единственное доступное действие в этом случае — удалить клуб целиком
- При удалении клуба соревнования, созданные от его лица (`Competition.organizingClubId`), не удаляются — они остаются, просто без владельца-клуба

**Team** (команда внутри клуба)
- `id`
- `clubId`
- `name: String`
- `sportType: KindOfSport` — переиспользует существующий enum `KindOfSport` (`domain/src/main/java/com/competra/domain/models/KindOfSport.kt`: `Orienteering`, `CrossCountrySki`, `TrailRunning`), уже привязанный к `Competition.kindOfSport`. Отдельный enum для команд не нужен.

Клуб может иметь несколько команд одного и того же вида спорта (например, «Юниоры» и «Взрослые» по ориентированию — раздельно).

**TeamMember** (членство участника клуба в конкретной команде)
- `teamId`
- `clubMemberId` (или `userId`)
- `role: TeamRole` — `CAPTAIN | MEMBER`

Роль капитана скопирована на уровень команды, а не клуба целиком: участник может быть капитаном одной команды и рядовым участником другой команды того же клуба одновременно. Участник клуба может состоять в нескольких командах клуба сразу.

**ClubJoinRequest** (заявка на вступление в клуб)
- `id`
- `clubId`
- `userId`
- `status: PENDING | APPROVED | REJECTED`

Подать заявку можно только если у клуба `allowJoinRequests == true`. Заявка видна в двух местах:
- заявителю — статус его собственной заявки
- Founder/Admin клуба — список входящих заявок с возможностью одобрить/отклонить

Приглашение конкретного пользователя в клуб (минуя заявку) — отдельный флоу, рассмотреть **позже**, в MVP не входит.

### Связь с существующими сущностями

- **Competition**: добавляется опциональное поле `organizingClubId`. Создать соревнование от лица клуба может участник с ролью `FOUNDER` или `ADMIN` в этом клубе. Существующая сущность `Organizer` (конкретные люди с ролями MAIN/JUDGE/SECRETARY/COURSE_SETTER/OTHER — `domain/src/main/java/com/competra/domain/models/orienteering/Organizer.kt`) не меняется и продолжает описывать роли конкретных людей на конкретном событии; клуб — это просто дополнительный «владелец» соревнования в UI.
- **OrienteeringParticipant**: при регистрации на соревнование участник, состоящий в клубе/команде, получает возможность выбрать клуб/команду из списка. Возможность ввести произвольный текст (нынешнее поведение `commandName`) сохраняется как fallback — для участников вне клубной системы.
  - Реализация (MVP, Android + eSport + web): у участника текст `commandName` (подпись в протоколе) + nullable `team_id` (FK на `teams`, `ON DELETE SET NULL`). Подпись своей команды — «Клуб (Команда)», клуба без команды — название клуба.
  - `GET /event/orienteering/competitions/{id}/registration-team-options` — свои команды по `kindOfSport` соревнования, подписи из протокола, `suggestedCommandName` (прошлый выбор → единственная команда → единственный клуб → прошлый свободный текст; при нескольких командах — пусто).
  - Клиент отправляет `teamId`, только если текст в поле совпадает с подписью своей команды (отредактировал — свободный текст). Сервер проверяет членство, иначе отбрасывает `teamId`.
  - При сохранении участника организатором (`upsert`/`upsertAll`) `team_id` сохраняется, пока подпись не изменилась (без учёта регистра/пробелов): клиенты `teamId` не присылают.
  - Одинаковый свободный текст у разных участников — просто одинаковая подпись, команда не создаётся. Чтобы подписи совпадали, в подсказках есть названия из протокола.
  - `GET /clubs/match?name=` — подсказка «такой клуб есть в Competra»: клуб с тем же названием, где пользователь не состоит; кнопка открывает карточку клуба.
  - Правка команды после регистрации — не в MVP (отменить и зарегистрироваться заново; после закрытия регистрации — только организатор).

### Синхронизация

Клубы, команды, членство и заявки работают **только online** — без offline-first подхода, который используется для остального приложения (`:core:sync`, `ConflictResolver`, `SyncCenterWorker`). Создание/редактирование клуба, добавление участников и т.п. требуют интернет-соединения; специальный офлайн-кейс для этого не предусматривается.

### Открытые вопросы (не в рамках MVP)

- Флоу «пригласить пользователя в клуб напрямую» (без заявки)
- Более сложные сценарии передачи Founder при нескольких кандидатах, аудит смены ролей
- Публичная модерация клубов (например, блокировка клуба администрацией платформы)

## Часть 2. Рейтинг соревнований (следующий этап, зависит от Части 1)

### Сущность рейтинга

**Rating** (`RatingSeries`)
- `id`
- `name`
- `ownerClubId` — владелец рейтинга; создавать рейтинг и добавлять в него соревнования может Founder/Admin клуба-владельца
- список соревнований, включённых в рейтинг (`RatingCompetition`: `ratingId`, `competitionId`)
- правила подсчёта очков (см. ниже)
- без привязки к сезону/году на первом этапе — рейтинг не имеет ограниченного временного окна

### Начисление очков

- MVP: фиксированная таблица очков по месту, взятая за основу от системы IOF
- Более продвинутая версия (адаптивный рейтинг, учитывающий количество участников, ранг соревнования, квалификацию участников) — заложена как направление развития, но не реализуется на первом этапе
- Очки берутся из уже существующего поля `rank` в `OrienteeringResult` (`domain/src/main/java/com/competra/domain/models/orienteering/OrienteeringResult.kt`) — пересчитывать места заново не нужно
- Пропуск соревнования участником = 0 очков за это соревнование (просто не прибавляется). Порога обязательного участия (минимума стартов для попадания в зачёt) нет — участник виден в рейтинге, даже если бежал всего один старт из серии

### Группы участников

Рейтинг считается в разрезе групп участников (мужчины/женщины/возрастные категории и т.п. — сущность `ParticipantGroup`, `domain/src/main/java/com/competra/domain/models/ParticipantGroup.kt`, поля `title`, `gender`, `minAge`, `maxAge`). Поскольку в разных соревнованиях группы могут называться и делиться по-разному, при добавлении соревнования в рейтинг нужен **маппинг групп**: у рейтинга задаётся канонический список групп, а группы конкретного соревнования сопоставляются с этими каноническими группами (можно предлагать сопоставление автоматически по `gender` + возрастному диапазону, с ручным подтверждением/правкой организатором).

### Идентификация участника между соревнованиями

Приоритет: `userId` (если участник зарегистрирован). Fallback для участников без аккаунта: сравнение по фамилии + имени + дате рождения; если дата рождения не указана — по фамилии и имени (менее точно, приемлемо для первого приближения).

### Кросс-проектность

Как и клубы — сначала Android + eSport backend, веб позже.
