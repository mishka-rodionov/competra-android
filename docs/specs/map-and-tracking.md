# Геопривязанная карта и трек участника — дизайн-спека

Статус: **брейнсторм завершён, готово к формальному планированию/реализации**.

> **Частично устарело (23.09.2026).** Часть 2 (трек участника) и раздел «Клиентский рендер» заменены спекой [`live-tracking.md`](live-tracking.md). Часть 1 реализована иначе: карта хранится на уровне дистанции (`distances.map_url` + углы), рендер — osmdroid/Leaflet.

Кросс-проектность: домен затрагивает `competra-android`, backend `eSport` и `mapper` (C++). **Web не входит в первый этап** — по аналогии с pace-per-leg фичей, competra-web добавляется отдельной задачей позже.

## Мотивация

После завершения соревнования организатор хочет опубликовать спортивную карту, привязанную по координатам к OpenStreetMap, и показать зрителям трек прохождения дистанции конкретным участником (если тот бежал с телефоном/трекером). Идея развивается в сторону live-трекинга: зритель видит участника на карте, пока тот ещё бежит.

## Существующий фундамент (важно — не переизобретать)

- `mapper` (форк OpenOrienteering Mapper) уже умеет полноценную геопривязку карты (`core/georeferencing.h`, состояние `Georeferencing::Geospatial`) с переводом любой точки карты в WGS84 через `toGeographicCoords()`.
- Этот метод уже используется в `iof_course_export_full.cpp` — при экспорте IOF XML КП получают `<Position lat lng>`, если карта геопривязана.
- `eSport` (`IOFXmlParser.kt`) уже парсит эти координаты, они лежат в `ControlPoint.latitude/longitude` (`domain/.../orienteering/ControlPoint.kt`) и используются в фиче темпа — см. [[project_pace-per-leg-feature]].
- `mapper` умеет экспортировать растр карты (PNG) с world file (`gui/print_widget.cpp`, `templates/world_file.h/cpp`), но только пиксель↔спроецированные координаты карты, без WGS84 и без варианта для PDF.

Вывод: цепочка «геопривязка в mapper → реальные координаты в домене» уже проверена в бою для точек. Не хватает переноса этого на растр карты целиком и на GPS-трек участника.

## Часть 1. Публикация геопривязанной карты

### Экспорт из mapper

Не использовать world file + отдельный CRS (клиенту тогда нужна репроекция средствами PROJ). Вместо этого — новый экспортёр в `mapper`, по образцу `iof_course_export_full.cpp`:
- рендерит карту в PNG;
- координаты 4 углов изображения считает той же `Georeferencing::toGeographicCoords()`, что уже используется для КП;
- пишет их в сайдкар (JSON) рядом с PNG.

Углы нужны все четыре (не bounding box), потому что карта может быть повёрнута (магнитное склонение) — прямоугольный bounding box в этом случае исказит наложение.

### Сущность в eSport

**CompetitionMap**
- `id`
- `stageId` (см. `orienteering/Stage.kt`) — карта привязывается к этапу, а не к соревнованию целиком: на многодневных стартах разные дни могут использовать разные карты/районы
- `imageUrl`
- `topLeft`, `topRight`, `bottomLeft`, `bottomRight`: `Coordinates` (переиспользовать `domain/.../Coordinates.kt`)
- `uploadedAt`

Один этап может иметь несколько `CompetitionMap` (открытый вопрос — см. ниже), но MVP предполагает одну карту на этап.

### Клиентский рендер

Движок карты — **MapLibre GL Native** (Android SDK), не Google Maps SDK. Причина: приложение распространяется в трёх флейворах (`gplay`/`rustore`/`huawei`), и Google Maps SDK завязан на Play Services, которых на rustore/huawei нет. MapLibre — чистый OSM-тайловый рендер без зависимости от Google.

Растровое наложение карты делается через `ImageSource` MapLibre, который принимает URL растра + 4 угловые координаты и сам выполняет перспективное искажение — то есть ложится прямо на данные `CompetitionMap` без дополнительной геообработки на клиенте.

MapLibre GL Native сама по себе бесплатна и open source (BSD-2-Clause, форк Mapbox GL Native до перехода Mapbox на проприетарную лицензию) — без API-ключа, без квот, без телеметрии. Но она только рендерит тайлы, а не хостит их: источник тайлов для базовой OSM-подложки — отдельный выбор (сырые `tile.openstreetmap.org` для продакшна не годятся по usage policy OSM Foundation; варианты — провайдер с бесплатным тиром или самостоятельный хостинг тайлов). На оверлей `CompetitionMap` это не влияет — это собственный PNG-ассет с бэкенда, без внешней зависимости.

Экран размещается в `:core:eventdetails` как новый пункт рядом с `details`/`live_results`/`results` (тот же модуль уже хранит навграф для деталей события).

## Часть 2. Трек участника

### Режим работы: live + офлайн-фолбэк

Участник включает трекинг перед стартом. Пока есть сеть — точки трека почти в реальном времени уходят на сервер, и зрители видят движение на карте. Если сети нет (типично для леса) — точки копятся локально и выгружаются, как только связь появится, а полная выгрузка гарантированно происходит после финиша, даже если по пути не было ни одного успешного live-апдейта.

Это **не** тот же механизм, что `:core:sync`/`ConflictResolver` — там разрешаются конфликты редактирования результатов. Трек — упорядоченный append-only поток без конфликтов, нужна более простая очередь: локальный буфер (Room) → периодическая попытка отправки батча → при неудаче копится дальше → принудительный полный флаш на финише. Инфраструктуру `:core:sync` (`NetworkAvailabilityObserver`, паттерн WorkManager-воркера) стоит переиспользовать, а не писать с нуля, но как отдельный, более простой флоу.

### Сущности в eSport

**Track**
- `id`
- `participantId`
- `stageId`
- `startedAt`, `finishedAt: Long?`
- `status`: `RECORDING | UPLOADED | FAILED`

**TrackPoint**
- `trackId`
- `lat`, `lng`
- `elevation: Double?`
- `timestampMs`
- `accuracyMeters: Double?`

### Запись на клиенте

Foreground service с `ACCESS_FINE_LOCATION` (+ `ACCESS_BACKGROUND_LOCATION`, если экран может быть выключен во время бега) и `foregroundServiceType="location"`. Требует **явного согласия участника** на трекинг — публикация live-геопозиции затрагивает приватность, это не то же самое, что молчаливая синхронизация результатов. Предлагается булево поле согласия при регистрации на старт или отдельный тумблер перед стартом (открытый вопрос — где именно).

Модульно код записи трека (foreground service + доменная логика буферизации) не вписывается ни в `:feature:center` (там про дистанции/чипы/результаты), ни в `:core:eventdetails` (там про просмотр зрителем). Рекомендация — новый модуль `:core:tracking`: общая логика записи трека (используется участником во время бега) и, возможно, общий код отрисовки полилинии (переиспользуется и в live-режиме, и в просмотре опубликованного трека зрителем).

### Отображение зрителю

Полилиния в WGS84 поверх `ImageSource` карты из Части 1 (или прямо на голых OSM-тайлах, если карта ещё не оверлейнута — см. порядок реализации). Точки уже взятых КП (из `OrienteeringResult`/сплитов) можно наносить поверх трека как маркеры с подтверждённым временем — для сверки с «сырым» GPS-треком, у которого в лесу типично сильная погрешность (многолучевое распространение сигнала). Map-matching трека к дистанции — не в MVP.

## Открытые вопросы (не в рамках MVP)

- Источник тайлов для базовой OSM-подложки (self-host vs провайдер с бесплатным тиром вроде MapTiler/Stadia Maps) — конкретный выбор не сделан, для первого этапа не блокирует реализацию.
- Несколько карт на один `stageId` (например, отдельная карта для спринт-квалификации и финала в один день) — пока не поддерживается, `CompetitionMap` предполагает одну карту на этап.
- Где именно участник даёт согласие на live-трекинг (при регистрации vs тумблер перед стартом) и можно ли его отозвать посреди забега.
- Live-канал зрителя: WebSocket/SSE vs короткий поллинг — конкретный протокол не выбран.
- Map-matching GPS-трека к линиям дистанции для сглаживания ошибок в лесу.
- Impact на батарею при длительной записи трека (многочасовые марафонские дистанции по ориентированию) — нужны эмпирические тесты частоты сэмплирования.

## Порядок реализации

1. Экспортёр карты в `mapper` + `CompetitionMap` в eSport + просмотр геопривязанной карты в `:core:eventdetails` (без треков) — самостоятельно полезно уже сейчас для публикации карт после соревнования.
2. Запись трека участником (`:core:tracking`, foreground service, локальный буфер) + пост-финишная выгрузка + показ готового трека зрителю поверх карты из шага 1.
3. Live-канал: апдейты трека в реальном времени, пока участник ещё бежит.
4. competra-web — по готовности, отдельная задача.
